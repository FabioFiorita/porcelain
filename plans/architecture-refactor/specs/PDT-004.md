# PDT-004 — Export, back up, and reset pre-launch data only with exact authorization

- Status: Blocked
- Batch: 4
- Domain: Project Data
- Depends on: PDT-001, PDT-002, PDT-003, DAT-001
- Governing decisions: 009, 015
- Primary exemplar: no

## Objective

Define the exact export/backup/reset protocol for disposable and human-authored pre-launch data without performing any real-data mutation. This unit remains blocked until the human authorizes named targets and recovery terms.

## Why this unit exists

Clean version-1 launch proof cannot authorize deletion of `~/.porcelain`, application userData, or repository `.porcelain` material. Historical conversion code is not permission to erase it.

## Current behavior and evidence

- Inventory roots include user config/access/action trust, per-project Board/Actions/Scope/Notes/Review/Evidence documents, home records, and migration markers.
- Decision 015 permits code to stop reading obsolete formats after cutover but prohibits silent erase of human material.
- `migrate-home.ts` currently copies/purges historical data; it is a deletion target after an authorized clean-state path.

## Scope

- Produce only an authorization checklist, fixture protocol, export format, and recovery verification.
- Do not execute export, backup, reset, purge, rename, or overwrite against real data.

## Non-goals

- Do not infer authorization from a clean checkout, an accepted architecture decision, a test fixture, or a request to write this recipe.
- Do not delete migrations or touch user/config/project paths.

## Target ownership and public surface

A future authorization names every absolute target, owner, material/disposable classification, export destination, encryption/access policy, integrity manifest, restore command, recovery window, exact destructive command, operator, and explicit human approval. Export is read-only until approval; reset is restricted to named targets after export verification.

## Behavior to preserve

Preserve every real record, secrets/permissions, corruption backups, atomic write behavior, and intentional current-format default until explicit authorization.

## Legacy behavior to delete

Authorize no legacy deletion. Home/flat migrations, old aliases, and old evidence readers remain untouched by PDT-004.

## Ordered implementation

1. Add a non-executable authorization template under `plans/architecture-refactor/` that contains all Target ownership fields and an unfilled approval field.
2. Create isolated fixture roots representing each classified record and test export manifests/restoration without resolving a live home or checkout path.
3. Validate that an authorization refuses relative paths, duplicate targets, missing classification, missing restore verification, or absent approval.
4. Stop at the blocker. Do not add a runnable reset script or a command that resolves real paths.

## Tests

- Fixture-only export/restore manifest tests.
- `pnpm test` and `pnpm lint` pass; no test reads a real home or checkout companion root.

## Validation and evidence

Blocked evidence consists of passing isolated fixture tests and a completed-but-unapproved template. Confirm no real-data command exists.

## Forbidden shortcuts

- Do not run recursive deletion, overwrite, migration purge, or in-place conversion.
- Do not mark Ready/Landed without explicit human approval for all named targets and recovery terms.

## Completion criteria

Blocked. The exact blocker is explicit human authorization for named real-data export/backup/reset targets after recovery verification. No real-data mutation is authorized by this recipe.

## Handoff

An approved successor executes only the named plan and records export integrity/restore evidence; it does not retroactively authorize other roots.
