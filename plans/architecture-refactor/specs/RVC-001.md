# RVC-001 — Put Review-comment behavior behind operations and a version-1 dual-writer cutover

- Status: Landed
- Batch: 2 — focused behavior exemplars
- Domain: review
- Depends on: CON-021, ERR-001, RT-005, DAE-001, TST-002, DAT-001
- Governing decisions: [003](../decisions/003-application-operations-own-orchestration.md), [005](../decisions/005-contracts-own-the-wire.md), [006](../decisions/006-compose-explicit-capabilities.md), [009](../decisions/009-treat-realtime-as-recoverable-signals-and-streams.md), [010](../decisions/010-type-expected-failures-and-validate-boundaries.md), [011](../decisions/011-test-the-boundary-that-owns-the-risk.md), [015](../decisions/015-make-a-clean-pre-launch-cutover.md)
- Primary exemplar: no

## Architecture reviewer rulings

- Copy the landed Board daemon exemplar `BRD-002` / `apps/daemon/src/features/board/`; this recipe does not establish a second server pattern.
- This unit owns the atomic daemon + CLI cutover to one strict version-1 comments document. Unversioned arrays are rejected; there is no compatibility reader or migration fallback.
- Public failures are `review.unavailable`, `review.comment-not-found` with a non-empty string `commentId`, and operation-level `request.invalid` for an inverted add range.
- The persistence capability follows the landed Board exemplar: `read` + `transact`, with pure planning helpers owning comment transitions.
- The comments document is bounded at `512 * 1024` bytes.

## Objective

The six existing Review-comment procedures (`reviewComments`, `addReviewComment`, `editReviewComment`, `deleteReviewComment`, `clearResolvedReviewComments`, `resolveReviewComment`) each invoke exactly one bound Review-comment operation over an injected atomic comments store; daemon and CLI share one strict version-1 comments document at `active-review/comments.json`; successful mutations publish exactly one operation-owned `review.changed` fact for that project path after the durable write; expected failures replace silent missing-id success.

## Why this unit exists

Comments are the first optimistic client exemplar (`RVC-002`). Server success/failure boundaries, authoritative add output, and post-write `review.changed` must be stable before shared client optimism. Board already proved the dual-writer + operations + composition pattern (`BRD-002`); comments still call `stores/comment-store.ts` directly from `router/review.ts` with an unversioned array and silent missing-id mutations.

| --- | --- |
| `reviewComments` | `['review.unavailable']` |

### Six operations (transport-independent)

Wire still uses `repoPath`; operations may name the field `projectPath` internally when mapping from input (Board uses `projectPath` end-to-end because Board wire already does). For comments, map `input.repoPath` → store `projectPath` at the router/operation boundary without changing the public schema.

| Operation factory | Input (from contract) | Success value | Expected failures |
| --- | --- | --- | --- |
| `createListReviewComments` | `{ projectPath }` from `repoPath` string | `ReviewComment[]` sorted `createdAt` desc, then stable `id` | `review.unavailable` |
| `createAddReviewComment` | repoPath + path + optional anchors + body | authoritative `ReviewComment` | `review.unavailable`, `request.invalid` (inverted range) |
| `createEditReviewComment` | repoPath, id, body | `void` (`undefined`) | unavailable, not-found |
| `createDeleteReviewComment` | repoPath, id | `void` | unavailable, not-found |
| `createResolveReviewComment` | repoPath, id, resolved | `void` | unavailable, not-found |
| `createClearResolvedReviewComments` | repoPath | `void` | unavailable only |

`ReviewCommentOperations` is a frozen object of the six bound functions (same shape as `BoardOperations`).

### Capability port

```ts
type ReviewCommentStore = {
  read(projectPath: string): Promise<ReviewCommentStoreResult<CommentsFileV1>>
  transact(
    projectPath: string,
    change: (current: CommentsFileV1) => ReviewCommentChangeResult,
  ): Promise<ReviewCommentTransactResult>
}

type ReviewCommentClock = { now(): number }
type ReviewCommentIds = { create(): string }
type ReviewCommentChanges = {
  publish(change: { type: 'review.changed'; projectPath: string }): void
}
```

Store results distinguish `review.unavailable` only. Domain rejects (`review.comment-not-found`, inverted-range as `request.invalid` if planned in the transaction helper) never inspect native error text. Operations publish **after** `transact` returns durable success and **never** on reject/unavailable.
