## Objective

Search owns the three existing file-name, text, and code-search procedures through directly testable
operations and narrow injected capabilities, while the flat wire names and all current result
semantics remain unchanged.

## Why this unit exists

The residual `apps/daemon/src/router/files.ts` currently combines Search orchestration with the Files
router boundary. That leaves the Search intention invisible, prevents capability-fake operation
tests, and keeps the Search pure rules in a horizontal `apps/daemon/src/search/` directory.

## Target ownership and public surface

The target daemon API is a flat merge with no wire nesting:

```ts
type SearchGit = Readonly<{
  listFiles(repoPath: string): Promise<string[]>
  searchText(repoPath: string, query: string): Promise<SearchTextOutput>
  searchCode(
    repoPath: string,
    options: Omit<SearchCodeInput, 'repoPath'>,
  ): Promise<SearchCodeOutput>
}>

type SearchScope = Readonly<{
  hiddenPaths(repoPath: string): Promise<ReadonlySet<string>>
}>

type SearchOperations = Readonly<{
  searchFiles(input: SearchFilesInput): Promise<SearchFilesOutput>
  searchText(input: SearchTextInput): Promise<SearchTextOutput>
  searchCode(input: SearchCodeInput): Promise<SearchCodeOutput>
}>
```

`createSearchOperations` receives both capabilities as required construction arguments; it has no
default adapter and does not import a concrete Git or scope module. The composition root supplies:

```ts
{
  git: {
    listFiles: gitListSearchFiles,
    searchText: gitGrep,
    searchCode: gitSearchCode,
  },
  scope: { hiddenPaths: hiddenPathsForRepo },
}
```

The router uses `procedureCatalog.searchText`, `procedureCatalog.searchCode`, and
`procedureCatalog.searchFiles` directly for input/output validation. The operations use the
contract's stable `repoPath` boundary, while the capability names describe their owned ability and
never expose a router or UI type.

## Behavior to preserve

- A file-name query whose trimmed value is empty returns `[]` without calling either capability.
  Nonempty file-name queries read the Git search list and hidden scope in parallel.
- Search candidates include tracked, untracked, and loose individually ignored files supplied by
  `gitListSearchFiles`; collapsed ignored directories and `.DS_Store` entries remain excluded by
  the Git adapter. Every visible file's ancestor directories are offered, hidden files and hidden
  subtrees are removed without hiding siblings with a shared name prefix, and absolute hidden
  paths are interpreted relative to the declared repository root.
- Fuzzy subsequence matching preserves contiguous/basename scoring, existing tie/order behavior,
  and the 50-result limit. The output maps directories to `kind: 'dir'` and files to
  `kind: 'file'` exactly as the Search contract requires.
- Text search preserves the current Git grep literal behavior, no-match empty result, 500-match
  cap, and parsed `{ path, line, text }` shape. Code search preserves regex/literal mode,
  case-sensitivity, include/exclude globs, context hunks, whole-file cap, and `truncated` output.
- Git list stale-while-revalidate, identity reuse, native parsing, and ignored-file policy remain
  in their existing Git adapter tests; the Search operation does not duplicate or reimplement them.
- Strict input rejection and strict output validation remain transport behavior. A malformed input
  never calls a capability; a malformed capability output reaches the existing internal-unexpected
  public error path through tRPC.
