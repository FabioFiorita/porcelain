# DAE-001 — Establish explicit daemon composition and bound router operations

- Status: Draft
- Batch: 0
- Domain: Daemon composition
- Depends on: ARC-002
- Governing decisions: 001, 003, 004, 006, 014
- Primary exemplar: yes

## Objective

Make daemon router construction explicit: a composition root constructs a typed operation catalog
and passes narrow bound operations into router factories. The per-request tRPC context remains
request context, and the wire router remains flat and unchanged.

## Why this unit exists

`api.ts` imports singleton routers and `router/board.ts` imports store functions directly. There is
no seam for a domain operation to receive narrow capabilities or for a test to replace an operation
deterministically.

## Current behavior and evidence

- `api.ts` exports singleton `router` via `t.mergeRouters` and `AppRouter = typeof router`.
- `trpc.ts` context is `{ auth: AuthIdentity }`.
- `server.ts` imports the singleton and passes it to `createDaemonHttp`.
- `router/board.ts` directly calls `stores/board-store.ts`; its six flat procedure names are public.

## Scope

- Add `apps/daemon/src/daemon-composition/daemon-operations.ts` and
  `apps/daemon/src/daemon-composition/create-daemon-router.ts`.
- Change `apps/daemon/src/trpc.ts`, `api.ts`, `server.ts`, and current router exports to use the
  composition factory.
- Add `apps/daemon/src/daemon-composition/create-daemon-router.test.ts`.

## Non-goals

- Do not move a domain to `apps/daemon/src/features`, change authentication/listeners/wire paths,
  alter a procedure schema, replace stores/adapters, or introduce a service locator.

## Target ownership and public surface

`daemon-operations.ts` exports:

```ts
export type DaemonOperations = Readonly<Record<never, never>>
export interface CreateDaemonRouterOptions { operations: DaemonOperations }
export function createDaemonOperations(): DaemonOperations
```

`createDaemonOperations` returns `Object.freeze({})`. Its empty catalog is intentional: no domain
operation exists until its migration adds a required non-optional catalog property and converts its
router in the same change. `createDaemonRouter(options)` returns the merged router; `api.ts` exports
that factory and `AppRouter` as its return type, plus current File/Repo type re-exports, but exports
no process-global router.

Each existing `apps/daemon/src/router/*.ts` exports `create<CurrentRouter>Router()` returning its
present router object. `createDaemonRouter` passes no dependency to a legacy router until its domain
migration requires one. A migrated router factory accepts exactly its required bound operations,
never the complete catalog, an index signature, or an optional field. `DaemonTrpcContext` continues
to carry `auth` and the `requestId` supplied by `ERR-002`, never operations or adapters.

## Behavior to preserve

- One `initTRPC` builder and one flat procedure namespace remain.
- Every procedure retains its input/output, authorization, error behavior, and flat wire name.
- `server.ts` builds the router once before its loopback listener accepts a request.
- Existing direct store behavior remains until each owning migration replaces it.

## Legacy behavior to delete

- Delete process-global app-router construction in `api.ts` and its import by `server.ts`.
- Delete the auth-only tRPC context type.

## Ordered implementation

1. Add `daemon-operations.ts` with the exact public surface and frozen empty constructor.
2. Leave request context ownership in `trpc.ts`; retain the same `t`, `publicProcedure`, and
   `adminProcedure` behavior using `ctx.auth`.
3. Convert every current router singleton to a named factory, preserving each router object literal,
   its order, and its direct store implementation verbatim.
4. Implement `createDaemonRouter({ operations })`, call every router factory in the exact current
   merge order, merge them with the same `t.mergeRouters`, and retain `operations` only as the typed
   composition input from which later migrations pass a narrow property to one router factory.
5. Make `api.ts` re-export that factory and derive `AppRouter` from it; retain File/Repo type exports.
6. In `server.ts` create operations and router inside `main()` immediately before `createDaemonHttp`.
   Do not create either per request.
7. Test composition by asserting the complete current flat procedure key set and calling `boardCards`
   through a composed router caller against a temporary project-board fixture.

## Tests

- `create-daemon-router.test.ts` locks the exact flat key set and calls `boardCards` through the
  composed router.
- Existing daemon/router tests continue unchanged.
- `pnpm lint` proves architectural checks still pass.

## Validation and evidence

Run `pnpm --dir apps/desktop test ../daemon/src/daemon-composition/create-daemon-router.test.ts`,
then `pnpm test` and `pnpm lint`. Record the locked router key set and that no HTTP/listener factory
changed.

## Forbidden shortcuts

- Do not put adapters, stores, Node I/O, or environment reads in `DaemonOperations`.
- Do not use `Record<string, unknown>`, optional future operations, or a compatibility singleton.
- Do not put the operation catalog in tRPC context, construct routers per request, or resolve
  operations from middleware.

## Completion criteria

- One explicit composition root builds the daemon router.
- Router factories receive operations from composition without changing request/auth semantics.
- All legacy procedures remain flat/callable and the initial catalog is empty/frozen.
- The focused central-Vitest test, `pnpm test`, and lint pass.

## Handoff

BRD-002 adds required `board` operations, changes only `createBoardRouter` to require them, and
proves that router no longer imports the Board store. Later domain migrations repeat this pattern.
