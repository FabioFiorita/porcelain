# PRO-001 — Version daemon HTTP and the Remote `daemonInfo` contract

- Status: Landed
- Batch: 0 — architecture and contract foundations
- Domain: protocol / daemon HTTP
- Depends on: `CON-021`, `ERR-003`
- Governing decisions: [005](../decisions/005-contracts-own-the-wire.md), [010](../decisions/010-type-expected-failures-and-validate-boundaries.md), [015](../decisions/015-make-a-clean-pre-launch-cutover.md)
- Primary exemplar: no

## Objective

Define protocol version `1` and expose it through the Remote `daemonInfo` contract, without changing
which daemon HTTP requests are accepted.

## Why this unit exists

The daemon currently gives clients no structured way to compare their protocol before a request
crosses the boundary. Version enforcement must wait until owned clients send the header.

## Current behavior and evidence

`apps/daemon/src/router/daemon.ts` serves `daemonInfo` bound to
`procedureCatalog.daemonInfo.output`, which is `daemonInfoOutputSchema` in
`packages/contracts/src/remote/remote.contract.ts` — a `.strict()` object of exactly
`version`/`host`/`platform`/`arch` with no protocol field. `packages/contracts/src/protocol.ts` does
not exist yet; this recipe creates it and exports it from the package root. Mobile parses
`daemonInfo` with this same schema (`apps/mobile/src/lib/daemon/procedures/connection.ts`), so the
schema, daemon, and clients move together in one commit. The HTTP boundary is
`apps/daemon/src/net/daemon-http.ts`, but `PRO-004` changes its acceptance rules. `CON-021` (Landed)
already removed the horizontal package-root daemon-info schema, so this recipe extends one canonical
Remote contract instead of creating two competing wire truths.

## Scope

Own `packages/contracts/src/protocol.ts`, the Remote daemon-info schema/record supplied by `CON-002`,
`apps/daemon/src/router/daemon.ts`, and their contracts/router tests. `daemon-http.ts` is explicitly
out of scope until `PRO-004`.

## Non-goals

Do not alter daemon HTTP acceptance, repository-owned HTTP clients, pairing UI, session hello/ready,
Web/mobile adapters, authentication grants, transport choice, or real-time subscriptions.

## Target ownership and public surface

`protocolVersion` is the literal `1`. `daemonInfo` returns it as `protocolVersion`; the strict Remote
output schema owns that field. `PRO-002` derives the request header from this value and `PRO-004`
later validates it at the HTTP boundary.

## Behavior to preserve

Preserve existing daemon-info fields, all HTTP acceptance behavior, pairing authorization semantics,
CORS/listener behavior, and all non-tRPC/non-pairing routing.

## Legacy behavior to delete

Delete only the unversioned `daemonInfo` output. `PRO-004` deletes acceptance of versionless tRPC and
pairing requests after `PRO-002` has updated callers.

## Ordered implementation

1. Add the version constant/schema and extend the Remote daemon-info output exactly once.
2. Return the literal version from `router/daemon.ts`.
3. Add output tests proving daemon-info exposes only the literal shared protocol version.

## Tests

Cover `daemonInfo` output parsing and router behavior, including rejection of malformed values by the
strict Remote output schema.

## Forbidden shortcuts

Do not infer version from app release, add an HTTP gate early, use a query parameter, or change client
adapter code in this recipe.

## Completion criteria

- [ ] `daemonInfo` and the shared protocol contract expose literal version `1`.
- [ ] Existing HTTP acceptance remains unchanged until `PRO-004`.
- [ ] Router/contract tests prove the versioned daemon-info surface.
- [ ] Focused tests, repository lint, full verify, and diff check pass.
- [ ] One commit lands only `PRO-001`, marks recipe/catalog Landed, leaves a clean worktree, provides
      the README review packet, and finishes without pushing.

## Handoff

`PRO-002` supplies harmless headers from repository-owned HTTP callers; `PRO-004` then enforces
them. `PRO-003` uses the same version in the real-time hello/ready handshake.
