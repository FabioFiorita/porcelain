# PDT-006 — Prove Project Data corruption, atomicity, ownership, and completion gate

- Status: Draft
- Batch: 4
- Domain: Project Data
- Depends on: PDT-002, PDT-005, DAT-001
- Governing decisions: 006, 009, 015
- Primary exemplar: no

## Objective

Make Project Data completion mechanical: every owned record uses strict v1 storage with explicit corruption/atomic behavior, no generic side effects, and no completed-domain legacy ledger.

## Why this unit exists

Project Data is the resilience owner for atomic JSON, corruption backup, serialized read-modify-write, and companion layout policy. Completion without proof would leave these guarantees scattered in channels/stores.

## Current behavior and evidence

- `home-channel.ts` and `project-channel.ts` currently own mixed JSON behavior; several consumers default after parse failure.
- `strict-json-document` foundation defines a no-caller v1 primitive.
- Inventory classifies atomic tmp+rename, backups, limits, and diagnostics as real resilience.

## Scope

- Apply strict primitive/adapters to all completed Project Data records and add a Project Data completion lint.
- Prove corruption, incompatible version, temp cleanup, concurrent writes, ownership boundaries, and clean v1 behavior.

## Non-goals

- Do not reset/export real data, resurrect migration readers, or adopt Review/Board/Actions domain record policy.
- Do not delete evidence/Review compatibility; REV-009 owns that.

## Target ownership and public surface

Project Data adapters expose only their named record capability and strict `ReadStrictJsonDocument` outcomes. Corruption is backed up/diagnosed; incompatible version remains untouched; mutation serialization is per document; root-manifest ownership maps each file to exactly one product domain.

## Behavior to preserve

Preserve backup bytes, same-directory atomic replacement, file limits, explicit defaults for missing current-format documents, and visibility disposition behavior.

## Legacy behavior to delete

Delete only completed Project Data legacy ledger entries and generic-channel ownership shims after all records/callers pass the target proof. Do not delete historical records.

## Ordered implementation

1. Wire strict document adapter into each Project Data-owned root manifest record.
2. Add integration matrix tests: missing default, valid read/write, corrupt backup, incompatible untouched, too-large, failed write, sequential concurrent writes, and no temp residue.
3. Add ownership test that every companion root is claimed once and Project Data does not own Review/Board/Actions payload schemas.
4. Add architecture lint checks that feature operations have no router/tRPC import and generic channel has no product policy.
5. Remove completed Project Data legacy paths from `DOMAIN_MIGRATIONS` only after the matrix and zero-hit source checks pass.

## Tests

- Central Vitest strict-adapter matrix using temporary directories.
- Root-manifest ownership test and architecture fixtures.
- `pnpm test`, `pnpm lint`, `pnpm verify` pass.

## Validation and evidence

Record matrix outcomes and corruption backup contents, ownership map, domain registry change, and zero legacy policy imports.

## Forbidden shortcuts

- Do not convert corrupt/incompatible data to defaults.
- Do not broaden a baseline or leave a generic channel exception.
- Do not claim completion while any Project Data operation reaches legacy migration code.

## Completion criteria

All Project Data records have one strict owner and matrix proof; legacy ledger is zero; completion gate and full commands pass.

## Handoff

Other domains use Project Data capabilities without importing storage adapters.
