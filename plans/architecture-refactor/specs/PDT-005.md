## Objective

`apps/daemon/src/project/migrate-home.ts` and `migrate-active-review.ts`, their
tests, the migration-only trust grandfathering, and four dead deprecated aliases
no longer exist anywhere under `apps/` or `packages/`; a permanent guard fails
`pnpm lint` if any of those identifiers return; and a repo holding a legacy flat
companion still opens, reads as empty, and keeps its files byte-for-byte.

## Why this unit exists

PDT-001 landed the strict v1 companion root, PDT-002/PDT-003 landed the Project
Data operations and client adapters, REV-002 removed the last migration call from
`review-store.ts`, and PDT-004 recorded the human-only clean-state authorization.
The migration modules are therefore unreferenced source that still advertises a
second, historical layout. Decision 015 wants exactly one version-1 storage path;
PDT-006 cannot certify the domain complete while a home→repo migrator sits in the
tree.

### Legacy-layout outcome after this deletion (no new failure surface is invented)

Because the migrators already have zero callers at `9a651ea6`, deleting them
changes no runtime behavior. A repo still holding the legacy flat companion
(`review.json`, `comments.json`, `reviewed.json`, `intent/`, `evidence/` at the
companion root, and/or home channel records under `~/.porcelain`) behaves exactly
as it does today: the v1 root is ensured, the manifest is written when missing,
every companion read returns its empty default, and the legacy files are neither
read nor removed. There is no silent migration and no silent erase. The only
explicit failures are the three landed `project-data.manifest-*` codes above. For
a real repository the human's remedy is the manual clean-state procedure in
`plans/architecture-refactor/authorization/pdt-004-human-reset.md`, which the
executor never runs.
