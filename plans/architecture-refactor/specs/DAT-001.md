# DAT-001 — Establish strict version-1 persisted envelopes and atomic document behavior

- Status: Draft
- Batch: 0
- Domain: Project Data
- Depends on: DAE-001, TST-002
- Governing decisions: 003, 004, 006, 009, 014, 015
- Primary exemplar: no

## Objective

Add a strict version-1 JSON document primitive for future Project Data adapters. It distinguishes
missing, malformed, oversized, and incompatible documents; writes through a same-path temporary
file plus rename; preserves corrupt bytes; and does not adopt, migrate, delete, reset, or reinterpret
any existing persisted record.

## Why this unit exists

Existing channels mix generic JSON I/O with product side effects and several callers use an empty
value after any read failure. The target needs domain-owned versioned documents with durable-write
and corruption guarantees, but converting live records before their owning schemas/cutover tests
exist risks data loss.

## Current behavior and evidence

- `net/home-channel.ts` provides atomic JSON, serialized mutation, validation, and corrupt backup.
- `net/project-channel.ts` performs project JSON I/O but also triggers home migration, Git-exclude
  policy, and Review watcher registration.
- Current stores read mixed unversioned `board.json`, `actions.json`, `scope.json`, `layers.json`,
  and Review records; several readers return an empty value after parse/read failure.
- Atomic tmp+rename and corrupt backups are retained resilience; home purge and flat active-Review
  migration are legacy deletion work owned elsewhere.

## Scope

- Add `apps/daemon/src/project-data/strict-json-document.ts` and its focused test.
- Define strict envelope/read-result types for later domain adapters.
- Use TST-002's temporary-directory fixture to prove real durable-file behavior.
- Add no production caller in this unit.

## Non-goals

- Do not modify, migrate, delete, rename, purge, seed, or reset `config.json`, access records,
  action trust, any existing `.porcelain` record, home records, or active/archived Review data.
- Do not change `home-channel.ts`, `project-channel.ts`, `migrate-home.ts`, or
  `migrate-active-review.ts`.
- Do not treat an old unversioned JSON value as version 1 or add a persistence singleton/service.

## Target ownership and public surface

`strict-json-document.ts` exports:

```ts
export const PERSISTED_FORMAT_VERSION = 1 as const
export type PersistedEnvelope<Value> = { version: 1; value: Value }
export type ReadStrictJsonDocument<Value> =
  | { kind: 'missing' }
  | { kind: 'valid'; value: Value }
  | { kind: 'incompatible-version'; version: number }
  | { kind: 'corrupt'; backupPath: string }
  | { kind: 'too-large'; byteLength: number; maxBytes: number }
export interface StrictJsonDocumentOptions<Value> {
  path: string
  valueSchema: z.ZodType<Value>
  maxBytes: number
}
export interface StrictJsonDocument<Value> {
  read(): Promise<ReadStrictJsonDocument<Value>>
  write(value: Value): Promise<void>
}
export function createStrictJsonDocument<Value>(
  options: StrictJsonDocumentOptions<Value>,
): StrictJsonDocument<Value>
```

On disk, writes are exactly `JSON.stringify({ version: 1, value }, null, 2)` plus one newline.
Construction requires an absolute `path` and positive safe-integer `maxBytes`. A read checks size,
JSON, object envelope, numeric version, literal version 1, and `valueSchema` in that order.
Malformed/schema-invalid content is renamed to
`${path}.corrupt-<UTC ISO timestamp with colons replaced by dashes>` and returns `corrupt`.
An incompatible numeric version remains untouched and returns `incompatible-version`.

`write` creates the parent, writes a unique same-directory `.tmp-` file with mode `0o600`,
fsyncs it, renames it over `path`, then fsyncs the parent. Writes for one document are FIFO
serialized; a rejected write does not block the next write.

## Behavior to preserve

- Atomic replacement, bounded reads, and corruption preservation remain durable-file guarantees.
- Missing data remains distinct from corrupt or unknown-version data.
- Existing records retain present behavior because this unit connects no caller.
- No read begins historical migration, watcher registration, Git disposition work, or default seeding.

## Legacy behavior to delete

Delete no live compatibility behavior in DAT-001. Domain cutovers delete their own unversioned
readers only after clean-state and existing-data behavior are proven.

## Ordered implementation

1. Create the primitive with `node:fs/promises`, `node:path`, and Zod; reject invalid constructor
   options.
2. Encode the exact envelope. Use a monotonic in-process counter in the same directory for each temp
   name; no concurrent write shares a temp path.
3. Serialize writes with a promise tail that continues after rejection.
4. Return `missing` only for `ENOENT`. Return `too-large` before decoding and leave the source
   untouched. Rename malformed JSON, non-object/missing/non-numeric envelope versions, and invalid
   version-1 values to the corruption backup.
5. Allocate backups exclusively: on timestamp collision append `-1`, `-2`, and so on; never
   overwrite an existing backup.
6. For numeric versions other than 1, return `incompatible-version` without write, rename,
   fallback, or default seeding.
7. Add `strict-json-document.test.ts` using `withTemporaryDirectory`. Cover missing, valid
   write/read, byte limit, malformed backup, invalid version-1 backup, unknown-version preservation,
   sequential concurrent writes, and surfaced write failure.
8. Assert valid output's version/value, trailing newline, no `.tmp-` file, and POSIX `0o600`
   mode. Assert corrupt backups preserve original bytes and the original path no longer exists.

## Validation and evidence

Run the focused central-Vitest strict-document test, `pnpm test`, and lint. Record that no existing
persistence caller changed, plus the unknown-version and corrupt-byte preservation assertions.

## Forbidden shortcuts

- Do not return a default value for malformed, oversized, or unknown-version content.
- Do not delete corrupt/incompatible documents or interpret unversioned JSON as v1.
- Do not final-write with `writeFile(path, ...)` or use a temp path outside the final directory.
- Do not add migration, reset, cleanup, or discovery code.

## Completion criteria

- The primitive has strict v1 envelopes, distinct read outcomes, bounded reads, atomic writes, and
  corruption backups.
- It has no production caller and cannot alter existing persisted data.
- Focused central-Vitest test, `pnpm test`, and lint pass.

## Handoff

PDT-001 adopts this primitive for one Project Data-owned record only after its schema, clean-state
fixture, existing-data disposition, and cutover/deletion steps are specified. Later adapters reuse it.
