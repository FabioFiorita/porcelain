# BRD-003 — Define shared Board client semantics

- Status: Ready
- Batch: 1 — Board primary exemplar
- Domain: board
- Depends on: BRD-001, BRD-002, TST-001
- Governing decisions: [005](../decisions/005-contracts-own-the-wire.md), [007](../decisions/007-share-nonvisual-client-behavior.md), [008](../decisions/008-give-each-client-state-one-owner.md), [009](../decisions/009-treat-realtime-as-recoverable-signals-and-streams.md), [010](../decisions/010-type-expected-failures-and-validate-boundaries.md), [011](../decisions/011-test-the-boundary-that-owns-the-risk.md), [012](../decisions/012-enforce-the-target-architecture.md), [013](../decisions/013-use-ten-canonical-product-domains.md), [015](../decisions/015-make-a-clean-pre-launch-cutover.md)
- Primary exemplar: yes

## Objective

Client-runtime will own one typed Board cards query identity, five Board mutation consequence definitions with reversible optimistic transitions, and the exhaustive `board.changed` notification-to-query mapping used by both clients.

## Why this unit exists

Web embeds Board cache keys, five optimistic mutations, rollback and a raw `board` event in `apps/web/src/hooks/use-board.ts`; mobile maintains its own descriptor, `['boardCards']` invalidation array, and event map. BRD-001 and BRD-002 establish the canonical daemon contract and behavior; this unit establishes the common client semantic layer before either client changes UI.

## Current behavior and evidence

- Web `hooks/use-board.ts` reads `boardCards`, optimistically adds/updates/moves/deletes/clears cards, rolls back on failure, then invalidates. `hooks/use-board.test.ts` characterizes move/add/clear/update rollback and reconciliation.
- Web app-event logic in `hooks/use-app-events.ts` invalidates `boardCards` for raw event `board`.
- Mobile `features/board/use-board.ts` reads `boardCards`, uses `BOARD_INVALIDATIONS = ['boardCards']`, is invalidate-only, and relies on `lib/daemon/app-events.ts` for raw event mapping.
- Mobile Board descriptors and `BoardCard` types are inside `lib/daemon/procedures/review.ts`; BRD-005 owns their deletion.
- BRD-001 (Landed) owns the canonical Board modules under `packages/contracts/src/board/`
  (`boardProcedures` = the canonical six, exported but not yet catalog members; fixtures;
  `board.changed`). BRD-002 (Landed) publishes the notification only after durable success and
  serves the legacy wire names over the new operations until BRD-004's swap.

## Scope

- Add `packages/client-runtime/src/board/{board-queries,board-mutations,board-notifications,board-reconciliation}.ts` and their colocated `.test.ts` files.
- Add `packages/client-runtime/src/board/index.ts` and the `./board` package export.
- Add no app files and no daemon files.

## Non-goals

- Do not create React hooks, QueryClient calls, tRPC links, WebSocket clients, Zustand stores, Board components, or app test harness adapters.
- Do not define Board wire schemas, public errors, notifications, routers, operations, stores, persistence, protocol versions, or fixtures; BRD-001 and BRD-002 own them.
- Do not coordinate Board → Review handoff; it is a local presentation handoff until a separate server intention requires a daemon workflow.

## Target ownership and public surface

- `@porcelain/client-runtime/board` will export `BoardCardsQuery`, `boardCardsQuery`, `BoardMutation`, `boardMutations`, `BoardOptimisticSnapshot`, `applyBoardOptimisticTransition`, `rollbackBoardOptimisticTransition`, `reconcileBoardMutation`, and `boardNotificationEffects`.
- `boardCardsQuery(projectPath)` will return `{ domain: 'board', name: 'cards', projectPath }` with the exact canonical `ProjectPath` contract type from BRD-001. It is the only Board query identity.
- `boardMutations` will contain five keyed definitions: `create`, `update`, `move`, `delete`, and `clearColumn`. Each binds exactly one BRD-001 canonical procedure, declares `affectedQueries(input)` as `[boardCardsQuery(input.projectPath)]`, and declares `requiresAuthoritativeRefetch: true`.
- `applyBoardOptimisticTransition(cards, mutation, input, optimistic)` will return the changed card collection and an exact `BoardOptimisticSnapshot`. `optimistic` contains an adapter-provided `temporaryId` and `now` for create/move ordering; it has no ambient clock or ID generator.
- Create appends `{ id: temporaryId, title, body, status, order: now, createdAt: now }`; update patches supplied title/body; move changes status and `order: now`; delete removes one id; clearColumn removes only the selected status. A transition against an absent id leaves the collection unchanged.
- `rollbackBoardOptimisticTransition(snapshot)` returns the pre-mutation cards exactly. `reconcileBoardMutation` replaces a temporary create card with the canonical create result when supplied and otherwise returns the optimistic collection; every mutation still requires the declared authoritative refetch.
- `boardNotificationEffects(notification)` accepts only the BRD-001 `board.changed` notification and returns `[boardCardsQuery(notification.projectPath)]`. It has no default branch and no raw event string.

## Behavior to preserve

- Board remains live-refreshed after an agent, CLI, Web, or mobile Board write.
- Web’s immediate add/update/move/delete/clear feedback and failure rollback remain available; the shared definitions make the same reversible behavior available to mobile.
- The daemon remains authoritative for ids, ordering, validation and persisted values; a successful Board mutation always refetches the Board collection.
- Board data remains in TanStack Query, not a Zustand store. Board selection, card draft, phone column and local failure presentation remain application state.

## Legacy behavior to delete

- Delete no app-local hook, descriptor, invalidation array, raw event map, or schema in this unit; BRD-004 and BRD-005 delete their respective callers atomically.
- Do not export procedure-name strings, `AppEvent`, local Board schema types, or a generic invalidation helper from client-runtime.

## Ordered implementation

1. Verify BRD-001 exposes canonical Board contract types/procedure descriptors, `board.changed`, and Board fixture builders; verify BRD-002 publishes the notification only after a durable successful write.
2. Implement `board-queries.ts` with the single typed cards identity and tests for stable equal input and distinct Project paths.
3. Implement `board-reconciliation.ts` with the five pure transitions, exact snapshot rollback, temporary-create reconciliation and absent-card behavior.
4. Implement `board-mutations.ts` by binding BRD-001 procedure descriptors to the cards identity and reconciliation functions; do not import a transport adapter.
5. Implement `board-notifications.ts` as an exhaustive mapping from the contract notification to the cards identity.
6. Export only the documented Board surface from `board/index.ts`; add the package export and no pass-through app wrapper.
7. Test every definition directly through `@porcelain/contracts/testing` fixtures and `@porcelain/client-runtime/testing/daemon-mock`, without React rendering.

## Tests

- `board-queries.test.ts`: same Project path produces equal identity; different Project paths produce distinct identity.
- `board-reconciliation.test.ts`: create/update/move/delete/clear transitions, unchanged absent id, exact rollback, temporary id replacement, and authoritative-refetch declaration.
- `board-mutations.test.ts`: each mutation names exactly one canonical procedure and affects only cards for its input Project.
- `board-notifications.test.ts`: a valid `board.changed` fixture affects one cards identity and malformed/unrelated notification fixtures are rejected by the contract mock.
- No E2E or component test belongs to this unit.

## Forbidden shortcuts

- Do not place framework hooks, a global cache, ambient `Date.now`, ambient random ids, transport clients, or app imports in client-runtime.
- Do not call a mutation from another mutation or encode required Board behavior in the notification map.
- Do not omit the authoritative refetch after optimistic reconciliation or use a broad domain/environment invalidation.
