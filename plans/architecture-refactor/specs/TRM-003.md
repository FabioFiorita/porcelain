## Objective

Client-runtime owns one transport-neutral Terminal stream state machine for request correlation,
attachment intent, scrollback ordering, epoch/sequence validation, and explicit stream recovery.

## Why this unit exists

Web apps/web/src/lib/daemon.ts and mobile apps/mobile/src/lib/daemon/terminal.ts independently
generate request ids, track attached ids, correlate replies, route scrollback, and reattach after a
socket reconnect. That duplication lets the two clients disagree about stale replies, stream gaps,
and whether a disconnected PTY is still honestly attached.

## Current behavior and evidence

- packages/contracts/src/terminal/terminal.stream.ts is the only public Terminal wire source. Its
  TerminalClientFrame requires a non-empty reqId on every command; TerminalServerFrame contains
  terminal:created, terminal:attached, terminal:data, terminal:exit, both paste successes, and
  correlated terminal:error.
- apps/daemon/src/features/terminal/terminal-stream-gateway.ts sends an attach snapshot before
  later live output. An attach snapshot carries { epoch, sequence }; data and exit frames advance
  that sequence within one epoch. PTYs survive a socket drop and are attached per socket.
- packages/client-runtime/src/session/client-runtime.ts currently rebuilds a partial inbound
  Terminal union from three schemas and drops terminal:error. It must forward the complete
  contract-owned server union before the new Terminal state machine can correlate typed failures.
- apps/web/src/lib/daemon.ts owns pendingCreates, pendingAttaches, pendingPastes, pendingFiles,
  attachedIds, reconnect reattach, and scrollback listeners. Its AttachResult still contains the
  deleted found sentinel and its fire-and-forget commands omit required reqId values; TRM-004 owns
  that adapter cutover.
- apps/mobile/src/lib/daemon/terminal.ts owns a second request-id/timeout map, attachedIds, and
  reconnect attach loop; TRM-005 owns that adapter cutover. apps/mobile/src/lib/daemon/session.ts
  consumes the session runtime's exported TerminalServerFrame type.
- packages/client-runtime/src/session/recovery.ts proves the local idiom for pure, injected
  freshness tracking: no ambient clock, timers, randomness, sockets, or UI imports, and no replay
  of missed data. The Terminal state machine follows that boundary but owns byte-stream ordering
  separately from the session change sequence.

## Target ownership and public surface

### Request correlation

terminal-requests.ts exports these exact concepts:

~~~ts
type TerminalRequestKind = 'create' | 'attach' | 'paste-image' | 'paste-file'
type TerminalRequest = {
  readonly kind: TerminalRequestKind
  readonly reqId: string
  readonly deadline: number
  readonly frame: TerminalClientFrame
}
type TerminalRequestFailure =
  | { readonly reason: 'closed' }
  | { readonly reason: 'deadline' }
  | { readonly reason: 'server'; readonly error: TerminalPublicError }
type TerminalRequestOutcome =
  | {
      readonly kind: 'succeeded'
      readonly request: TerminalRequest
      readonly frame: TerminalRequestSuccessFrame
    }
  | {
      readonly kind: 'failed'
      readonly request: TerminalRequest
      readonly failure: TerminalRequestFailure
    }
~~~

TerminalRequestSuccessFrame is the exact union of terminal:created, terminal:attached,
terminal:image-pasted, and terminal:file-pasted extracts from @porcelain/contracts/terminal. The
public request registry factory is createTerminalRequestRegistry() and exposes:

~~~ts
type TerminalRequestRegistry = {
  readonly add: (request: TerminalRequest) => boolean
  readonly settle: (frame: TerminalServerFrame) => TerminalRequestOutcome | undefined
  readonly expire: (now: number) => readonly TerminalRequestOutcome[]
  readonly close: () => readonly TerminalRequestOutcome[]
  readonly has: (reqId: string) => boolean
}
~~~

add rejects an empty or already-pending reqId. settle accepts only the success discriminator
expected by that request kind or terminal:error whose reqId matches and whose optional id is absent
or equals the request target. A reply with a matching id but the wrong success kind, or a typed
error for another target, is ignored and remains non-destructive. expire(now) rejects every pending
request whose explicit deadline <= now; close() rejects all pending requests with { reason: 'closed' }.
Neither method reads the clock or starts a timer. A successful attach or create is returned to the
stream state machine so it can update attachment intent before the effect reaches an adapter.

### Stream state and public effects

terminal-stream.ts exports:

~~~ts
type TerminalRecoveryReason = 'reconnect' | 'epoch-changed' | 'sequence-gap'
type TerminalRecovery = {
  readonly reason: TerminalRecoveryReason
  readonly reattach: readonly string[]
  readonly refreshRoster: true
}

type TerminalStreamEffect =
  | {
      readonly type: 'request-succeeded'
      readonly request: TerminalRequest
      readonly frame: TerminalRequestSuccessFrame
    }
  | {
      readonly type: 'request-failed'
      readonly request: TerminalRequest
      readonly failure: TerminalRequestFailure
    }
  | { readonly type: 'data'; readonly frame: TerminalData }
  | { readonly type: 'exit'; readonly frame: TerminalExit }
  | { readonly type: 'recovery-required'; readonly recovery: TerminalRecovery }

type TerminalAttachmentStatus = 'awaiting-baseline' | 'running' | 'exited' | 'awaiting-reattach'
type TerminalAttachmentState = {
  readonly id: string
  readonly status: TerminalAttachmentStatus
  readonly epoch: string | undefined
  readonly sequence: number | undefined
}
~~~

TerminalStreamState and createTerminalStreamState() expose exactly these operations:

~~~ts
type TerminalStreamState = {
  readonly requestCreate: (input: TerminalCreateInput, requestId: string, deadline: number) => TerminalRequest | undefined
  readonly requestAttach: (id: string, requestId: string, deadline: number) => TerminalRequest | undefined
  readonly requestPasteImage: (input: TerminalPasteImageInput, requestId: string, deadline: number) => TerminalRequest | undefined
  readonly requestPasteFile: (input: TerminalPasteFileInput, requestId: string, deadline: number) => TerminalRequest | undefined
  readonly attach: (id: string) => boolean
  readonly detach: (id: string, requestId: string) => TerminalDetach | undefined
  readonly write: (id: string, data: string, requestId: string) => TerminalWrite | undefined
  readonly resize: (id: string, cols: number, rows: number, requestId: string) => TerminalResize | undefined
  readonly kill: (id: string, requestId: string) => TerminalKill | undefined
  readonly receive: (frame: TerminalServerFrame) => readonly TerminalStreamEffect[]
  readonly expire: (now: number) => readonly TerminalStreamEffect[]
  readonly close: () => readonly TerminalStreamEffect[]
  readonly reconnect: () => readonly TerminalStreamEffect[]
  readonly state: (id: string) => TerminalAttachmentState | undefined
  readonly desiredAttachments: () => readonly string[]
}
~~~

TerminalCreateInput, TerminalPasteImageInput, and TerminalPasteFileInput are the corresponding
contract command shapes with only reqId omitted. TerminalDetach, TerminalWrite, TerminalResize, and
TerminalKill are exact contract Extract<TerminalClientFrame, ...> types. The adapter supplies
requestId and deadline; the runtime serializes the id as the contract's reqId and never calls
randomUUID, Date.now, setTimeout, or any other ambient source.

requestCreate, requestAttach, and the two paste methods build one strict client frame, register it,
and return it to the adapter. They return undefined for invalid ids, duplicate pending request ids,
or an attachment operation already represented by an established/pending attachment. requestCreate
has no target id and records the daemon-created id only when its matching terminal:created reply
arrives. requestAttach records desired intent before sending and removes that intent if the request
closes or expires before a baseline arrives. Paste requests require a known desired running
attachment; they do not mutate stream state.

attach(id) records a non-empty desired attachment and returns whether it added new intent. It does
not send a frame. desiredAttachments() returns a stable id-ordered snapshot for an adapter's roster
reconciliation. state(id) reports awaiting-baseline for a newly created PTY until its first accepted
data/exit frame, running or exited after a baseline, and awaiting-reattach after a disconnect or
stream desynchronization. An established desired attachment remains in the map after close() and
after a natural exit; detach() and kill() remove it.

detach, write, resize, and kill are no-reply commands. They return no frame when id or requestId is
empty, when the session is unknown, or when the command is not valid for the current state. write
additionally rejects empty data and strings longer than MAX_TERMINAL_WRITE_CODE_UNITS; resize
requires positive integer dimensions; write and resize require a known running attachment; kill
accepts a known running or exited attachment. On a returned detach or kill frame the desired
attachment is removed immediately, so a later reconnect cannot resurrect an intentional local
removal. No-reply command errors do not create pending promises; an unmatched terminal:error is
ignored.

### Stream ordering and recovery

receive(frame) first gives correlated replies to the request registry. A matching terminal:attached
success applies its scrollback, status, epoch, and sequence baseline and emits the request-success
effect before any later data effect. A matching create success records the returned id as a desired
awaiting-baseline attachment. Paste successes and typed errors emit only their matching request
effect.

For terminal:data and terminal:exit, the state machine accepts only the following transitions:

1. A newly created awaiting-baseline session accepts the first frame as its baseline, records its
   epoch/sequence, and emits the data or exit effect. The create reply has no snapshot metadata, so
   this first frame is the honest baseline rather than reconstructed output.
2. A running/exited session accepts a frame only when its epoch matches and its sequence is exactly
   the previous sequence plus one. It records the new sequence and emits the frame effect.
3. A frame with the same epoch and sequence at or below the last accepted sequence is stale and is
   dropped idempotently.
4. A frame with a different epoch, a sequence gap, or data/exit arriving while an attachment is
   awaiting its attach baseline is dropped without exposing bytes. The session becomes
   awaiting-reattach and emits one recovery-required effect for that session; repeated frames while
   it waits do not emit repeated recovery effects.

An accepted exit records exited and keeps desired intent so the client may replay the final
scrollback/status on reconnect. reconnect() marks every desired attachment awaiting-reattach
(including exited sessions), returns one recovery-required effect with reason reconnect, all desired
ids in reattach, and refreshRoster: true, and emits no guessed data. close() rejects pending
requests and leaves established desired attachments intact; the adapter calls reconnect() after the
next session-ready boundary. An epoch mismatch or sequence gap returns the affected id in reattach
and also sets refreshRoster: true. requestAttach clears the awaiting state only after its matching
attach snapshot is accepted.

Protocol mismatch remains the terminal state owned by session/client-runtime.ts; this Terminal
state machine does not invent another mismatch representation. It also does not consume the session
change sequence, cache data, or replay writes/creates/paste bytes.

## Forbidden shortcuts

clients, define a second Terminal schema or error envelope, correlate by error messages, accept
stale/mismatched replies, apply data before an attach snapshot, turn a sequence gap into guessed
bytes, replay writes or creates after reconnect, treat reconnect as proof of freshness, consume the
session change sequence, or expose raw socket events. Do not reintroduce found, old paste-result
strings, empty reqId frames, or a second attachment map in either shared runtime module.
