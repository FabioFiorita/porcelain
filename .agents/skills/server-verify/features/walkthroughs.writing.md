# Durable walkthrough writing

The contract is `packages/contracts/src/walkthroughs/api.ts`. The writing routes require the paired fixture credential and its Origin.

1. Make a small committed or uncommitted fixture change on a branch and keep its base branch. Untracked non-ignored additions are part of the same change. POST `/api/worktrees/:worktreeId/walkthrough` with `{ "base": "refs/heads/main" }`. The response is the durable run, initially queued. Repeat the same request with the same base commit and content on the same branch while the attempt is queued, running or ready: the id must match and no second writer may start. After a failed attempt, an explicit start creates a new attempt; concurrent presses share that new attempt. Earlier failures remain stored. A second branch at the same head receives its own run; returning to a branch reuses its own current manual attempt. Automatic mode starts exactly once per repository and PR number, ever: another worktree, branch, head, restart or failed attempt never creates a second automatic run. The content-identity migration retires old pages, evidence and conversations while preserving handled PR markers, so upgrading cannot trigger another automatic run.
2. GET the same path: `walkthrough` is the latest ready run for the current branch, or the latest attempt when none is ready. `attempt`, when present, is the newer queued/running/failed run; its failure stays visible alongside the ready page. `outOfDate` compares the displayed run’s base commit and full content tree, not its head commit. Switching branches hides other branches’ runs. Subscribe to the worktree live channel: changes use `type: "walkthrough", change: "run"`.
3. Commit exactly the explained content: GET stays fresh and another start reuses the run. Edit, add or delete a file, or move the base: GET reports `outOfDate: true`; Update captures a new run. The original head remains for display and PR evidence. Captured files, hunks and diff are durable; edits during writing only make the result stale. Capture uses a temporary index and object directory outside the repository, preserves its bytes and ignores ignored files.
4. Existing PR evidence is addressed by GET `/api/worktrees/:worktreeId/walkthrough/:runId/assets/:assetId`; verify its media type and exact bytes. A missing asset or an asset belonging to another run returns the declared 404 JSON error, `Walkthrough evidence asset not found`. No PR means no PR evidence. Uncommitted content on top of the matching PR head is allowed; evidence still comes only from the PR.
5. PR attachment images may redirect: follow at most five HTTPS redirects, checking every destination against the GitHub image allowlist before requesting it. The public attachment chain from GitHub to `github-production-user-asset-6210df.s3.amazonaws.com` is allowed; unrelated S3 buckets and lookalike hosts must never be fetched.
6. Both writer passes exclude inherited MCP/plugin tools and repository hooks. Before each Codex pass, list effective MCP servers, explicitly disable each name, and read the effective list with those overrides; fail without starting the writer if either list is unreadable or any server remains enabled, including one forced on by managed settings. Codex progress is separate from the final answer file; prose progress must not reject valid final output.
7. Stop and reopen the application with the same disposable database while a writer is active. Running work becomes failed with an interruption message, queued work is dispatched, finished content and evidence remain readable. Shutdown drains the writer process group before persistence closes.

Run `apps/server/spec/integration/walkthroughs.integration.ts` and `apps/server/spec/integration/walkthroughs-restart.integration.ts` through the integration runner, then `apps/server/src/runtime/walkthrough-workflow.spec.ts`, `apps/server/src/adapters/walkthroughs/filesystem-transcript-reader.spec.ts`, `apps/server/src/adapters/walkthroughs/github-evidence-reader.spec.ts`, `packages/agents/src/walkthrough-writing/cli-walkthrough-writer.spec.ts`, `packages/walkthroughs/src/rules/qualify-walkthrough.spec.ts` and `packages/storage/src/db/migrate.spec.ts` by name. They use fake CLI executables, real SQLite and real Git for durable execution, filtering and qualification.

The default sandbox intentionally has no installed agent, sign-in or network. A real writer proof needs the host CLI through a bounded, owned verification bridge, using a public Porcelain change and the same read-only flags. Retain timing and cost from the ready state; never copy transcripts or credentials to evidence.

The walkthrough integration spec uses the built server and real SQLite, reaches all three walkthrough routes with valid credentials, and passes their actual validated-handler log through the unchanged route-coverage guard. This focused check establishes coverage of these routes; the global teardown guard is judged only by a full integration run.

## Walkthrough conversations

The contract is `packages/contracts/src/walkthroughs/conversations.ts`. Every route needs the paired credential and the Origin, under `/api/worktrees/:worktreeId/walkthrough/:runId/conversations`.

1. A walkthrough must be finished (`status: "ready"`). POST `.../messages` with `{ "anchor": { "kind": "walkthrough" } | { "kind": "stop", "title": "<exact stop title>" }, "text": "Why?" }`. The response is the conversation view with the developer message and its agent reply in state `answering`. An unknown stop, an unfinished run or a run from another worktree answers 404.
2. GET the run-scoped root for the view. The path's `runId` is the ready walkthrough displayed by the client. Every conversation operation validates that run belongs to the worktree and uses its same-branch history up to that run, irrespective of the current Git branch. A foreign-worktree run or a message outside that history returns 404. After a newer finished run on that branch, a stop whose title still exists keeps its anchor and the rest appear under `kind: "walkthrough"`. No conversation is deleted by a new commit or walkthrough.
3. Answers run in the walkthrough serial queue. A live notice `type: "walkthrough", change: "conversations"` follows a message, an answer, a retry, a save and a post. POST `.../messages/:messageId/retry` re-queues only a failed answer.
4. PUT `.../messages/:messageId/saved` with `{ "saved": true | false }`. POST `.../messages/:messageId/post` posts one message; POST `.../post-saved` posts that displayed run’s saved messages as one comment. With a pull request on the displayed run the outcome is `{ "status": "posted", "url": "..." }`, without one `{ "status": "brief", "text": "..." }`; nothing saved is `{ "status": "nothing" }`. Posting one message again returns the same URL and posts nothing; posting saved again finds nothing saved and answers `nothing`. GET `.../brief[?messageId=...]` reads the same text. Every start, with or without a pull request, records the GitHub repository from `origin`; posting goes only there, and when `origin` no longer matches it, posting answers 409 and posts nothing, while the brief stays readable. A message posts only when its own run recorded the same repository; `post-saved` posts the eligible ones and lists the rest in `notPosted`, and refuses with 409 when none are eligible.
   The post read phase freezes the run, repository, PR and selected message snapshots. The write phase validates that plan and refuses changes rather than replanning. A branch switch cannot redirect it.

5. On restart, answers still answering become failed with `This answer was interrupted. Ask again.`

Run `apps/server/spec/integration/walkthroughs.integration.ts` (fake agent and fake `gh`, real SQLite) and the auth sweep through the integration runner, then `apps/server/src/runtime/walkthrough-answers.spec.ts`, `apps/server/src/use-cases/walkthroughs/post-walkthrough-messages.spec.ts`, `packages/walkthroughs/src/rules/conversations.spec.ts`, `packages/agents/src/walkthrough-writing/cli-walkthrough-writer.spec.ts` and `packages/client/src/features/walkthroughs` by name.

A real answer needs the host's installed CLI through a bounded, owned bridge (the sandbox has no agent, sign-in or network), on a public Porcelain change with no pull request, so posting cannot reach GitHub. Report the answered state's `durationMs` and `costUsd`. Never post to a real pull request as a test: the post path is verified against a fake `gh`.

Freshness capture is separate from the saved page read: unsupported untracked Git filters or another content-identity failure leave the saved page readable and mark it out of date. Starting or updating still refuses conversion filters with a message naming them. Real-Git HTTP proof: `walkthroughs-fake-writer.integration.ts`.

Inspection-omitted sections are excluded from captured patch text and their paths are retained. Writer and fresh-answer prompts inline only uncommitted captures, in complete sections up to 128 KiB of UTF-8 patch bytes, and name omitted sections with read-only fallback instructions. Clean committed runs use the immutable base-to-head Git range rather than inline patches. Validation still uses the captured file/hunk set. Proof: `read-working-tree.spec.ts` and `writing-prompts.spec.ts`.

Freshness capture failures, including Git output limits and an untracked nested repository without a commit, preserve the saved page with `outOfDate: true`. Deduplication also compares the base reference, so replacing a deleted base ref at the same commit accepts a new run. Capture returns its own resolved head and tree; a commit after the earlier branch-range read must appear in both the writer head and the captured change. Focused proof: `git-walkthrough-head-reader.spec.ts`, `git-walkthrough-source-reader.spec.ts`, `sqlite-walkthrough-store.spec.ts`, and `walkthroughs-fake-writer.integration.ts`.
